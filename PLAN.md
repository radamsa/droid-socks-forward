# План разработки: SOCKS5-прокси на Android

> **Статус: реализовано (M0–M5, частично M6).**
> Собрано и проверено на эмуляторе API 36 (arm64): CONNECT по IPv4/домену,
> авторизация RFC 1929, 0.0.0.0 + предупреждение, EADDRINUSE, работа в фоне,
> нотификация со статистикой, индикатор VPN. 18 JVM-тестов `:core` проходят,
> `./gradlew build` проходит (lint чистый, остались только предупреждения о
> новых версиях библиотек). Не проверялось: реальный VPN-клиент, Android Go
> железо, долгие прогоны под нагрузкой.

Приложение слушает SOCKS5 на телефоне, само открывает исходящие TCP-соединения
и отдаёт их в сеть. Если на устройстве поднят системный VPN — трафик уходит
через него, потому что приложение является обычным клиентом ОС, а не отдельным
сетевым стеком.

---

## 1. Ключевые технические решения

| Вопрос | Решение | Почему |
|---|---|---|
| minSdk | **21** (Android 5.0) | Ниже 21 нет смысла: Kotlin/coroutines и RecyclerView требуют 21, а Android Go начинается с 8.1 (API 27). Запас покрытия максимальный. |
| compileSdk / targetSdk | 36 / 36 | В SDK уже стоит platform 36. |
| Язык | Kotlin | Короткий и безопасный код, корутины для I/O. |
| UI | **Views + ViewBinding + RecyclerView + Material Components** | Compose на 1 ГБ RAM и Go-устройствах заметно тяжелее (RAM, APK, старт). Views дают APK ~1 МБ и предсказуемое потребление. |
| Архитектура | 2 модуля: `:core` (чистый JVM) + `:app` (Android) | Протокол и движок тестируются юнит-тестами на JVM без эмулятора. |
| Фоновый режим | Foreground Service, тип `specialUse` (API 34+) | Единственный легальный способ держать сокет живым в фоне. |
| Настройки | SharedPreferences | Легче DataStore, на Go-устройствах меньше накладных расходов. |
| Статистика | In-memory `StateFlow`, обновление UI 1 раз/с | Без БД: счётчики не нужны после перезапуска сервиса. |
| UDP ASSOCIATE / BIND | **Не в v1** | Основной источник багов; браузеры и curl отлично работают через TCP CONNECT. Вынести в v2. |
| Аутентификация | Логин/пароль (RFC 1929), **опционально** | ~40 строк кода, закрывает главный риск «открытый прокси в Wi-Fi». |

### Почему трафик пойдёт через VPN

Механизм: VPN-приложение создаёт `tun`-интерфейс и добавляет маршрут по
умолчанию. Наши `Socket.connect()` — обычные сокеты процесса, ядро маршрутизирует
их в `tun`, VPN-приложение шифрует и отправляет наружу. Ничего специально
делать не нужно.

Три условия, которые надо проверить и описать в UI:

1. VPN должен быть **системным** (VpnService). «Прокси» в настройках Wi-Fi на нас
   не влияет — он перехватывает только HTTP-клиенты.
2. Приложение не должно быть **исключено** из VPN (per-app split tunneling,
   «раздельное туннелирование»). Иначе трафик уйдёт в обход.
3. Мы не вызываем `bindProcessToNetwork()` и не поднимаем собственный VpnService —
   иначе пришлось бы исключать себя из туннеля.

Проверка на практике: сравнить внешний IP с VPN и без, плюс смотреть счётчик
трафика в VPN-клиенте.

## 2. Архитектура

```
:core (JVM, без android.*)
  socks/Socks5Handshake.kt      разбор/сборка handshake, request, reply
  socks/Socks5Server.kt         accept-loop, лимит соединений, таймауты
  socks/ConnectionPump.kt       двусторонняя перекачка байт, half-close, счётчики
  model/ProxyConfig.kt          адрес, порт, auth, лимиты
  model/ConnectionInfo.kt       id, peer, target, state, байты, время старта
  model/ProxyStats.kt           totals + snapshot активных соединений
  api/ProxyEngine.kt            start/stop/state, колбэки наружу

:app
  service/ProxyService.kt       FGS, START_STICKY, bind-ошибки, нотификация
  service/ProxyNotifications.kt канал, обновление, кнопка «Стоп»
  data/SettingsRepository.kt    SharedPreferences + валидация
  ui/MainActivity.kt            статистика + список соединений
  ui/ConnectionsAdapter.kt      ListAdapter + DiffUtil
  ui/SettingsActivity.kt        адрес/порт/логин/лимиты
  ui/ProxyViewModel.kt          StateFlow из сервиса, throttle 1 Гц
  App.kt                        Application, DI вручную (без Hilt — лишний вес)
```

Состояние: сервис пишет в singleton-репозиторий (`object ProxyState`),
ViewModel подписывается на `StateFlow`. Никаких Binder-интерфейсов и
LocalBroadcast — проще и надёжнее.

## 3. Объём протокола SOCKS5

Реализуем:

- greeting: `VER=5`, методы `0x00` (no auth) и `0x02` (user/pass);
- выбор метода, отказ `0xFF` если не совпало;
- RFC 1929: `VER=1`, длина логина/пароля, ответ `0x01 0x00/0x01`;
- request: только `CMD=0x01 CONNECT`;
- `ATYP`: `0x01` IPv4, `0x03` домен, `0x04` IPv6;
- ответы: `0x00` success, `0x01` general failure, `0x02` not allowed,
  `0x03` network unreachable, `0x04` host unreachable, `0x05` refused,
  `0x07` command not supported, `0x08` address type not supported;
- домен резолвим **на телефоне** (аналог `socks5h`), чтобы DNS тоже шёл через VPN;
- таймауты: handshake 10 с, connect 10 с, idle 5 мин (настраиваемо);
- лимит одновременных соединений (по умолчанию 64) → при превышении сразу
  отвечаем `0x01` и закрываем;
- half-close: по EOF в одну сторону делаем `shutdownOutput()` на второй сокет и
  ждём завершения обратного потока;
- буферы 16 КБ, по одному на направление, освобождаются сразу после закрытия.

Осознанно **не** делаем в v1: `BIND`, `UDP ASSOCIATE`, GSSAPI, SOCKS4.

## 4. Экраны

**Main**
- большая кнопка Старт/Стоп + статус (Работает / Остановлен / Ошибка: порт занят);
- адрес для подключения крупным текстом: `192.168.1.42:1080` (плюс `127.0.0.1:1080`);
- суммарно: ↓ принято, ↑ отдано, активных / всего соединений, uptime;
- список соединений: `target host:port`, клиент, состояние, ↓/↑ по соединению;
- предупреждение, если слушаем `0.0.0.0` без пароля;
- подсказка про VPN, если VPN не активен (по `ConnectivityManager`, без фанатизма).

**Settings**
- адрес прослушивания: `127.0.0.1` / `0.0.0.0` / конкретный IP из списка
  интерфейсов (`NetworkInterface`, без разрешений);
- порт: 1024–65535 (ниже 1024 ядро не даст без root — валидируем и объясняем);
- логин/пароль (включается чекбоксом);
- лимит соединений, idle-таймаут;
- «Запускать при загрузке» — v1.1, не в MVP.

Изменения применяются только после перезапуска сервиса — показываем это явно,
чтобы не пересоздавать сокет на лету.

## 5. Сервис, жизненный цикл, батарея

- `ProxyService : Service`, `START_STICKY`, `startForeground()` сразу в `onCreate`.
- Manifest: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE`, `INTERNET`,
  `POST_NOTIFICATIONS` (33+), `android:foregroundServiceType="specialUse"` +
  `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` = `socks5 proxy server`.
- `ContextCompat.startForegroundService()` — совместимо с API < 26.
- Канал нотификации создаём только на 26+; на 21–25 — обычная нотификация.
- Нотификация: `Прокси · :1080 · 3 соед. · ↓1.2 MB ↑300 KB`, action «Стоп»,
  `PendingIntent.FLAG_IMMUTABLE` только на 23+ (иначе падение на API 21–22).
- Обновление нотификации не чаще 1 раза в секунду.
- Ошибка bind (`EADDRINUSE`, `EACCES`) → статус «Ошибка» в UI + нотификация,
  сервис останавливается, кнопка Старт снова активна.
- Wakelock **не нужен**: ядро будит процесс на входящий пакет, FGS достаточно.
- Опционально: экран-подсказка «отключить оптимизацию батареи» для Xiaomi/Huawei.
- Edge-to-edge для targetSdk 35+ обрабатываем через `WindowInsetsCompat`.

## 6. Этапы

### M0. Каркас (0.5 дня)
Gradle KTS, version catalog, `:core` + `:app`, minSdk 21, R8 + shrinkResources,
базовый экран с кнопкой. **Готово:** пустое приложение собирается и ставится на
эмулятор API 21 и API 36.

### M1. Движок SOCKS5 в `:core` (1.5 дня)
Парсер/энкодер, accept-loop, CONNECT по IPv4/домену/IPv6, перекачка с
half-close, лимиты, таймауты. **Готово:** JVM-тест поднимает сервер на
`127.0.0.1:0`, тестовый клиент проходит handshake и получает данные от
локального echo-сервера; есть тесты на битые пакеты и неверный пароль.

### M2. Сервис и жизненный цикл (1 день)
FGS, нотификация, старт/стоп, обработка ошибок bind, `START_STICKY`.
**Готово:** прокси живёт при свёрнутом приложении и после блокировки экрана,
`curl` с ноутбука через `adb reverse` работает.

### M3. Основной экран (1.5 дня)
Статистика, список соединений с DiffUtil, throttle 1 Гц, состояние ошибки.
**Готово:** 50 параллельных загрузок не роняют UI, цифры совпадают с
`curl`-тестом, список корректно очищается при остановке.

### M4. Настройки и авторизация (1 день)
Адрес/порт/лимиты/auth, валидация, применение после рестарта, список IP.
**Готово:** невалидный порт не сохраняется, `curl --socks5 user:pass@...`
работает, без пароля — отказ `0xFF` при включённой авторизации.

### M5. Статистика и полировка (0.5 дня)
Точность счётчиков (AtomicLong), форматирование байт, uptime, сброс при старте.

### M6. Устойчивость (1 день)
Много соединений, медленный клиент, обрыв VPN, смена Wi-Fi → LTE, перезапуск
сервиса системой, нехватка памяти (лимит соединений), отсутствие сети.
**Готово:** 30-минутный прогон без утечек и падений, RSS стабилен.

### M7. Тестирование и матрица устройств (1 день)
JVM-тесты, ручные сценарии (ниже), прогон на Go-эмуляторе (1 ГБ RAM, low-RAM
образ) и на реальном устройстве.

**Итого: ~8 рабочих дней** на одного разработчика до релизного MVP.

## 7. Тестирование

**Автотесты (`:core`, JVM, без Android)**
- handshake: no-auth, user/pass, неподдерживаемый метод, обрыв на каждом байте;
- request: IPv4 / домен / IPv6, неизвестный CMD, неизвестный ATYP, обрезанные пакеты;
- pump: half-close, большие объёмы, медленный читатель, корректность счётчиков.

**Ручные сценарии**
1. `adb reverse tcp:1080 tcp:1080` на ноутбуке →
   `curl --socks5-hostname 127.0.0.1:1080 https://example.com` — базовая проверка
   без Wi-Fi-связности между устройствами.
2. Firefox: SOCKS5 + «Proxy DNS when using SOCKS v5» → открыть сайт, проверить,
   что DNS-запросы не утекают (Wireshark/личный DNS-лог).
3. VPN включён → внешний IP равен выходу VPN; VPN выключен → IP оператора.
4. Per-app split tunneling: исключить приложение из VPN → убедиться, что трафик
   ушёл мимо (ожидаемое поведение, фиксируем в документации).
5. Блокировка экрана на 10 минут → соединение не рвётся.
6. Занятый порт → понятная ошибка, без падения.
7. Переключение Wi-Fi ↔ LTE во время загрузки → соединение корректно падает,
   сервис продолжает слушать.

**Что проверить на Go-устройстве:** старт < 1 с, RSS < 60 МБ при 10 соединениях,
APK < 2 МБ, отсутствие ANR.

## 8. Риски

| Риск | Митигация |
|---|---|
| OEM-прошивки (Xiaomi, Huawei, Samsung) убивают FGS | Подсказка про автозапуск/оптимизацию батареи, тесты на реальных устройствах, `START_STICKY`. |
| Открытый прокси в чужой Wi-Fi | По умолчанию `127.0.0.1`, предупреждение при `0.0.0.0` без пароля. |
| Пользователь исключил приложение из VPN → утечка | Явная подсказка в UI и README. |
| Google Play: политика по `specialUse` FGS и приложениям-прокси | Заранее готовить обоснование; альтернатива — распространение APK/F-Droid. |
| IPv6/dual-stack: `0.0.0.0` не слушает IPv6 | Слушать `::` с `IPV6_V6ONLY=false` или два сокета; отдельный тест. |
| Память при 100+ соединениях на 1 ГБ RAM | Жёсткий лимит соединений, буферы 16 КБ, отказ новым клиентам с кодом `0x01`. |
| targetSdk 36: edge-to-edge, ужесточение фоновых запусков | Явная работа с insets, отказ от автостарта в v1. |
